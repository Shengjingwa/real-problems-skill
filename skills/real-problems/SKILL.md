# real-problems

## 适用对象

只修改已经保存在磁盘上、且属于以下三大类之一的规则与说明文件：

1. **AI 提示词、技能与工作流**：
   - **Agent Skill**：各类技能定义文件（如 `SKILL.md`）
   - **系统提示词与角色规范**：System Prompt、Agent 指令约束、格式模板
   - **多 Agent 协作路由**：工作流状态转移规则、任务交接契约、Eval 评测标准
2. **系统架构与工程规范**：
   - **Agent 指引与项目规则**：`AGENTS.md`、`.cursorrules`、系统规则配置
   - **架构决策与技术选型**：ADR（架构决策记录）
   - **工程标准与协作规范**：代码审查清单、分支管理规范、API 数据契约说明
3. **运维、安全与业务操作手册**：
   - **应急与运维预案**：故障止血 Runbook、数据库割接手册、灾备演练 SOP
   - **发布与环境规范**：金丝雀发布检查清单、环境搭建指南、权限审计 SOP
   - **产品与测试规范**：带有明确验收准则（AC / Given-When-Then）的需求规格与测试用例

**文件指针处理**：
检查对象文件中提到的其它文件路径（指针）。只有当原文明确要求修改该目标文件，且该文件已存在且属于上述类别之一时，才将其一并列入修改对象并通读全文；其余仅作读取、核对或参考的文件，一律不列入修改对象，本次不改动。

**前置阅读分流**：
当修改对象属于 **Agent Skill** 时，主 agent 与所有 subagent 在提交草案或修改文件前，必须通读 `writing-for-agents` 与 `SKILL-MECHANICS.md`；修改其它非 Skill 文档时跳过此项阅读。

**不适用场景（立即停止并指引正确途径，不自动调用）**：
- 纯代码运行时报错排查 → 使用排查类 skill（如 `diagnosing-bugs`）
- 业务需求与产品方案探讨 → 使用 `grilling`
- 从零新建 Agent Skill → 使用 `create-skill`
- 纯代码架构重构与拆模块 → 使用 `codebase-design`
- 文档既无现成判据也无法提炼出任何可客观检验的完成条件 → 立即停止，说明无法按真问题流程继续

---

## 真问题的定义

一条缺陷必须**同时满足以下两个条件**才算真问题：

1. **能准确定位**：能指出在对象中的具体位置、原句或可观察的行为。
2. **不改必定失败**：如果不修改，对象就无法达成它自己写明（或第 1 步获批提炼）的完成条件，或缺失关键的异常/退出分支导致执行卡死、逻辑死锁。

*注：对象的 id、斜杠命令和 description，除非用户明确要求修改，否则不纳入真问题清单。*

## 执行步骤与闸门

### 1. 定对象

1. 通读列入本次修改的每份文件全文。
2. **确定完成条件**：
   - 若原文中已写明明确的完成条件/判据，原样摘录并作为基准。
   - 若原文未显式列出完成条件，但包含明确的执行流程或目标，由 Agent 提炼 2~4 条核心候选判据，使用 `AskQuestion` 提交用户确认或补充；获批后作为本轮审查的完成条件基准。
   - 若文档完全无法提炼出可检验判据，立即终止本次流程。
3. 记录文件绝对路径、已确定的完成条件，以及用户声明本次不动的部分。
4. 逐一检查文件中的外部引用指针，按规则决定是否列入修改对象；未列入的记录排除理由。

**完成标准**：所有列入路径均存在且属于适用大类之一；完成条件全部摘自原文或已由人工确认获批；所有文件指针均已明确列入（并读完全文）或记录了排除理由。

---

### 2. 闸门：调研

使用 `AskQuestion` 发起多选（推荐项排在第一位并标注 `(Recommended)`），选项固定为：

- 核查对象自己引用的东西是否成立：命令、路径、目录名、外部规范或组件名 (Recommended)
- 其它（用户自行填写）
- 不调研

发送后立即停止，等待用户选择：
- **用户勾选「不调研」**：忽略其它勾选，在笔记的「调研」章节记录一行理由，直接进入第 3 步。
- **用户勾选「其它」**：执行前先检查核查目标是否明确、所需来源是否可访问、核查动作是否可执行；若不满足，用 `AskQuestion` 指明缺口让用户补充或改选。
- **用户勾选了调研类别**：
  1. 整理核查清单（包含编号、对象绝对路径、原文位置）。第一类调研必须覆盖对象中出现的全部命令、路径、目录名和组件/规范名。
  2. 若清单较长，按对象分批并行派发 subagent，每个任务仅提供对应清单与源码仓绝对路径，subagent 按需读取原文并核对。
  3. subagent 逐项回报：事实、一手来源、与原文的出入。调研只查证事实，不得给对象新增完成条件。最后汇总为一份调研报告。

**完成标准**：用户完成选择；选「不调研」已记录理由；选调研项已完成全部核查并生成字段齐全的汇总报告。

---

### 3. 派角度

1. 将第 1 步确定的全部完成条件，划分给 2~4 个互不重叠的角度（例如：正向指令可行性、禁令与异常分支可判定性、术语一致性等）。
2. 并行派发 subagent 分头审查。每个任务仅分配单一角度的完成条件及相关的调研事实。
3. 每个角度针对审查出的疑似问题，输出候选清单。每条候选必须包含三个字段：
   - **位置及原文**
   - **对应哪条完成条件**
   - **不改时能看见的失败（或缺失分支带来的死锁/卡死）**
   *(若该角度未发现问题，明确注明「无候选」)*

**完成标准**：角度数量为 2~4 个；每条完成条件恰好分配给一个角度；每个角度输出一份合并回报；每条候选三字段齐全（或为无候选）。

---

### 4. 筛真问题

1. **编号与合并**：为所有候选赋予唯一编号。合并同因同果的候选，合并项赋予新编号并记录来源编号；若有冲突，以对象原文为准裁决。
2. **核验真问题**：依据「真问题」的两大硬条件逐条审查候选，仅保留真问题。淘汰的候选各写一句具体的丢弃原因。
3. **关联调研事实**：为每条调研事实赋予唯一编号。能构成候选的转化为候选编号，不能构成的记入笔记「调研」章节（若撞上用户声明不动的部分，注明冲突内容）。
4. **记录终点去向**：建立去向表，确保每个候选编号和调研事实编号都有且仅有一个确定的最终归宿（进入清单或记录丢弃/调研理由），不得悬挂。
5. **记录笔记**：将真问题清单、丢弃原因及去向表写入笔记文件，并准备提交下一闸门。

**完成标准**：所有候选与事实编号均有唯一终点去向；清单中的每条问题均严格满足真问题定义。

---

### 5. 闸门：真问题

使用 `AskQuestion` 发起单选（推荐项在前并标 `(Recommended)`）：

- 按这份清单继续 (Recommended)
- 停

发送后立即停止，等待用户回复。

**完成标准**：用户选择继续。后续流程仅处理本次获批的清单；若后续清单内容或范围发生增删改，必须回到第 4 步重新过本闸门。

---

### 6. 改法与异议

按顺序派发两个 subagent 进行方案设计与交叉审查（仅交稿，不直接改文件）：

1. **写改法（subagent 1）**：针对获批清单中的每条真问题，逐条输出修改方案：
   - 对应哪条获批真问题
   - 改动位置（精确到标题和原句）
   - 具体怎么改（给出可直接替换的文字，或唯一的语义修改说明）
   - 允许改动的边界
   - 预期结果（改后哪项失败消失，为何对应完成条件会重新成立）
   - 潜在风险
   - 故意不改什么
2. **挑刺（subagent 2）**：审查上述改法稿，专门挑出：与清单不符、破坏现有完成条件、遗漏获批条目、超出修改边界等问题，作为「异议」。
3. **主 agent 裁决与定稿**：主 agent 逐条处理异议（采纳并调整改法，或依据原文驳回），整理出最终方案并写入笔记。

**完成标准**：每条获批真问题均有对应的具体改法；每条异议均有明确的采纳或驳回记录。

---

### 7. 闸门：最终方案

使用 `AskQuestion` 发起单选：

- 按这份方案改对象 (Recommended)
- 停

发送后立即停止，等待用户回复。

**完成标准**：用户确认按此方案修改。若方案的改法、边界或范围发生实质变化，必须回到第 6 步更新并重新过本闸门。

---

### 8. 改对象

1. **创建快照备份**：在编辑文件前，于系统临时目录创建唯一备份文件夹，无损备份每个修改对象的当前全文（包含未提交的工作区变更）。
2. **精准修改**：严格仅修改最终方案点名的位置与内容，不得引入方案外的变更。
3. **比对验收**：比对修改后文件与临时快照，核对 diff 是否与方案一致，确认真问题指出的可观察失败已消除，且未破坏原有完成条件。
4. **清理备份**：步骤结束或终止时清理临时备份目录。

**完成标准**：修改内容严格与最终方案一致且无额外改动；所有真问题对应的失败均已消除；对象原有的完成条件依然成立。

---

## 笔记规范

所有运行记录必须写入源码仓的 `docs/<父目录名>-<文件名>.md`。

**定位源码仓路径规则（按顺序取首个成立项）**：
1. 当前工作区根目录名为 `real-problems-skill` → 工作区根即为源码仓。
2. 本 skill 目录下存在 `source-root` 文件 → 读取第一行记录的绝对路径。
3. 均不成立 → 向用户询问源码仓绝对路径，获取后写入本 skill 目录下的 `source-root` 文件（该文件仅保存在本地，不提交进 git）。
