# real-problems

## 适用对象

只修改已经保存在磁盘上、且属于以下三大类之一的规则与说明文件：

1. **AI 提示词、技能与工作流**：
   - **Agent Skill**：各类技能定义文件（如 `SKILL.md`）
   - **系统提示词与角色规范**：System Prompt、Agent 指令约束、格式模板
   - **多 Agent 协作路由**：工作流状态转移规则、任务交接契约、Eval 评测标准
2. **系统架构与工程规范**：
   - **Agent 指引与项目规则**：`AGENTS.md`、`.cursorrules`、系统规则配置
   - **架构决策与技术选型**：ADR（架构决策记录）
   - **工程标准与协作规范**：代码审查清单、分支管理规范、API 数据契约说明
3. **运维、安全与业务操作手册**：
   - **应急与运维预案**：故障止血 Runbook、数据库割接手册、灾备演练 SOP
   - **发布与环境规范**：金丝雀发布检查清单、环境搭建指南、权限审计 SOP
   - **产品与测试规范**：带有明确验收准则（AC / Given-When-Then）的需求规格与测试用例

**文件指针处理**：
检查对象文件中提到的其它文件路径（指针）。只有当原文明确要求修改该目标文件，且该文件已存在且属于上述类别之一时，才将其一并列入修改对象并通读全文；其余仅作读取、核对或参考的文件，一律不列入修改对象，本次不改动。

**前置阅读分流**：
当修改对象属于 **Agent Skill** 时，主 agent 与所有 subagent 在提交草案或修改文件前，必须通读 `writing-for-agents` 与 `SKILL-MECHANICS.md`；修改其它非 Skill 文档时跳过此项阅读。

**不适用场景（立即停止并指引正确途径，不自动调用）**：
- 纯代码运行时报错排查 → 使用排查类 skill（如 `diagnosing-bugs`）
- 业务需求与产品方案探讨 → 使用 `grilling`
- 从零新建 Agent Skill → 使用 `create-skill`
- 纯代码架构重构与拆模块 → 使用 `codebase-design`
- 文档既无现成判据也无法提炼出任何可客观检验的完成条件 → 立即停止，说明无法按真问题流程继续

## 两类改动

本流程同时处理两类改动，它们进入清单的门槛不同，全程分开记录、分开列示，不得混为一谈。

### 用户指定改动

用户已经拍板、不需要论证的改动。典型是改名、改 `description`、换斜杠命令、调整术语叫法。

它**不过**下面真问题的两条杠。用户提出即成立，主 agent 的职责是原样记下诉求与目标，评估影响面，随其它改动一起在第 8 步原子执行——不是去论证它该不该改。

### 真问题

一条缺陷必须**同时满足以下两个条件**才算真问题：

1. **能准确定位**：能指出在对象中的具体位置、原句或可观察的行为。
2. **不改必定失败**：如果不修改，对象就无法达成它自己写明（或第 1 步获批提炼、第 5 步获批采用）的完成条件，或与真实项目代码/环境脱节导致执行报错，或缺失关键异常/退出分支导致死锁卡死。

*注：对象的 id、斜杠命令和 `description`，只能作为「用户指定改动」进入本流程，不进真问题清单。*

## 执行步骤与闸门

### 1. 定对象

1. 通读列入本次修改的每份文件全文。
2. **记录用户指定改动**：原样记下用户提出的每一项改动诉求与目标（新名字、新措辞等）。此处只登记，不评判、不论证、不立即改文件。
3. **确定完成条件**：
   - 若原文中已写明明确的完成条件/判据，原样摘录并作为基准。
   - 若原文未显式列出完成条件，但包含明确的执行流程或目标，由 Agent 提炼 2~4 条核心候选判据，使用 `AskQuestion` 提交用户确认或补充；获批后作为本轮审查的完成条件基准。
   - 若文档完全无法提炼出可检验判据，立即终止本次流程。
4. 记录文件绝对路径、已确定的完成条件，以及用户声明本次不动的部分。
5. 逐一检查文件中的外部引用指针，按规则决定是否列入修改对象；未列入的记录排除理由。

**完成标准**：所有列入路径均存在且属于适用大类之一；用户提出的每项指定改动均已原样登记；完成条件全部摘自原文或已由人工确认获批；所有文件指针均已明确列入（并读完全文）或记录了排除理由。

---

### 2. 闸门：调研与评审模式

调研的核心作用是**引入外部客观事实（Ground Truth），通过对照项目真实代码/环境或同类成熟规范，发现文档声称与现实脱节的硬伤以及遗漏的关键分支，防止闭门造车**。

用**一次** `AskQuestion` 同时发出下面两题（推荐项排第一位并标注 `(Recommended)`），发送后立即停止，等待用户回复。

**第一题 · 调研范围（多选）**：

- 调研项目代码与实际环境：对照核查文档声称的命令、脚本、路径、接口字段、环境变量与依赖在当前项目中是否真实存在与匹配 (Recommended)
- 对标同类规范与成熟实现：参考业界或同类项目的成熟流程，对照寻找对象文档中遗漏的关键异常处理、防御性校验或退出分支
- 其它（用户自行填写）
- 不调研

**第二题 · 评审模式（单选）**：

- **独立陪审团**：多名 subagent 各用不同模型，独立完成同一轮完整评审（调研 + 读全文 + 报候选），彼此不通气。擅长发现未知问题，重复即互相印证 (Recommended)
- **分区覆盖**：先集中调研只交事实，再按完成条件切成 2~4 个互不重叠的角度分头审查。上下文更省，易于证明没有漏检项

**分支处理**：
- **勾选「不调研」**：忽略调研的其它勾选，在笔记「调研」章节记录一行理由；评审模式的选择仍然生效。
- **勾选「其它」**：执行前先检查核查目标是否明确、所需来源是否可访问、核查动作是否可执行；若不满足，用 `AskQuestion` 指明缺口让用户补充或改选。
- **选独立陪审团**：不在本步单独执行调研，调研并入第 3 步由每名陪审员各自完成。本步只整理调研范围说明，随任务下发。
- **选分区覆盖**：在本步执行调研。整理核查与对比清单（含编号、对象绝对路径、原文声称位置、需对比核验的项目代码/外部规范目标）；清单较长时按对象或对比维度分批并行派发 subagent，任务仅提供对应清单与源码仓绝对路径。subagent 逐项回报：客观事实、一手代码/文档来源、与对象原文的出入或遗漏分支，最后汇总为一份调研报告。

**调研的硬边界**：调研只查证事实与提供对比证据，**不得**把外部做法直接写成对象的完成条件。若调研认为对象应当补上某条它自己没写的标准，写成**候选标准**单独编号列出，标明来源与理由，等第 5 步闸门由人决定是否采用。

**完成标准**：用户对两题都做出选择；选「不调研」已记录理由；选独立陪审团时，调研范围说明已整理好待随第 3 步任务下发；选分区覆盖且选了调研项时，已完成全部对比核查并生成字段齐全、有证据来源的汇总报告，且本步产出的每条新判据都已编号记为候选标准，没有任何一条被直接当作完成条件使用。

### 3. 独立评审

#### 评审阵容（模型分派规则）

需要派模型的位置有两处：本步的评审者，以及第 6 步的改法者与挑刺者。

硬要求只有一条：**独立上下文**——每个 subagent 在自己的上下文里作业，看不到同伴的结论。模型多样性是增强手段，不是准入门槛：不同模型的盲区不重叠，同一处被多个模型独立指出，置信度高于同一模型重复采样。值得优先争取，但缺了它流程照跑。

1. **用户点名了模型**：严格照办，不得改派。点名的模型不可用时不得静默替换，停下来说明哪个不可用、当前有哪些可用，等用户改派。
2. **用户没点名**：从当前可用模型里挑，尽量让同一轮的角色两两不同。
3. **可用模型不够**：照常派满，重复使用同一模型即可，并在笔记里标注哪些角色用了同一模型。同模型给出的重合结论在第 4 步不计入置信信号。

#### 分支 A · 独立陪审团模式

1. 派出陪审员，默认 3 名——够产生多数信号（2/3、3/3），用户可改数量。按「评审阵容」分派模型。
2. 每名陪审员拿到**相同的完整输入**：对象全文绝对路径、全部完成条件、用户声明不动的部分、第 2 步确定的调研范围。
3. 每名陪审员**独立**完成整轮工作：先做调研，再通读对象全文，再用调研所得对照分析问题。陪审员之间不共享结论，不得看到其它陪审员的回报。
4. 每份回报包含：本人调研拿到的事实与一手来源、候选清单、以及本人认为应补的候选标准（如有）。

#### 分支 B · 分区覆盖模式

1. 将第 1 步确定的完成条件与第 2 步的调研事实，划分给 2~4 个互不重叠的角度（例如：项目实际可行性对照、正向指令完整性、禁令与异常分支可判定性、术语一致性等）。
2. 并行派发 subagent 分头审查，每个任务仅分配单一角度的完成条件及相关调研事实。

#### 两种模式共用的候选格式

每条候选必须包含三个字段：

- **位置及原文**
- **对应哪条完成条件（或哪项项目实际对比脱节点、哪条候选标准）**
- **不改时能看见的失败（或执行报错、缺失分支带来的死锁/卡死）**

该评审者未发现问题时，明确注明「无候选」。

**完成标准**：
- 陪审团模式：陪审员数量等于默认值 3 或用户指定值；每名拿到对象全文与全部完成条件；每份回报在独立上下文中产出，未参考其它陪审员结论；模型按「评审阵容」分派，用了同一模型的角色已在笔记标注。
- 分区覆盖模式：角度 2~4 个；每条完成条件与调研事实恰好分配给一个角度；每个角度输出一份合并回报。
- 两种模式共同：每条候选三字段齐全，或该评审者标注为无候选。

### 4. 筛真问题

1. **编号与合并**：为所有候选赋予唯一编号。合并同因同果的候选，合并项赋予新编号并记录全部来源编号。
   - 陪审团模式下重复是**预期结果**，不是浪费：合并时记录该问题被几名陪审员独立指出，并单独标出其中涉及**几个不同模型**。不同模型的重合才是强信号，同一模型的多次重合只按一个信号计。清单先按不同模型数、再按陪审员人数降序排列。
   - 分区覆盖模式下重复罕见，没有重复就不合并。
   - 结论互相冲突时，以对象原文或项目客观代码事实为准裁决。
2. **核验真问题**：依据「真问题」的两大硬条件逐条审查候选，仅保留真问题。淘汰的候选各写一句具体的丢弃原因。产品缺口（别人有、但本对象的完成条件并不要求）一律淘汰，不得升级成真问题。
3. **处理候选标准**：把第 2、3 步收到的候选标准统一编号列出，写明来源、理由。若某条真问题**只**依赖某条候选标准才成立，在清单里标注「依据候选标准 Sn，待批」。
4. **关联调研事实**：为每条调研事实赋予唯一编号。能构成候选的转化为候选编号，不能构成的记入笔记「调研」章节（若撞上用户声明不动的部分，注明冲突内容）。
5. **分类成清单**：清单分两节写——「用户指定改动」照第 1 步登记原样列出，不做筛选；「真问题」列筛后结果。两节不合并、不互相改写。
6. **记录终点去向**：建立去向表，确保每个候选编号、调研事实编号和候选标准编号都有且仅有一个确定的最终归宿（进入清单、被采用、或记录丢弃/调研理由），不得悬挂。
7. **记录笔记**：将两节清单、候选标准、丢弃原因及去向表写入笔记文件，并准备提交下一闸门。

**完成标准**：所有候选、事实、候选标准编号均有唯一终点去向；真问题节每条均严格满足真问题定义，依赖候选标准的已标注待批；用户指定改动节与第 1 步登记逐条对应，无增无减。

---

### 5. 闸门：清单

`AskQuestion` 的 `prompt` 需完整承载四块内容：用户指定改动、真问题清单（含独立指出人数）、候选标准、丢弃原因。

发起单选（推荐项在前并标 `(Recommended)`）：

- 按这份清单继续 (Recommended)
- 停

发送后立即停止，等待用户回复。

**完成标准**：用户选择继续，即视为同时批准三件事——真问题清单、清单所依赖的候选标准（被采用后升格为本轮完成条件）、以及用户指定改动。后续流程只处理这份获批内容；若清单、候选标准或指定改动的内容与范围发生增删改，必须回到第 4 步重新过本闸门。

---

### 6. 改法与异议

按顺序派发两个 subagent 进行方案设计与交叉审查（仅交稿，不直接改文件），按「评审阵容」分派模型，优先让两者用不同模型。

无论模型是否相同，挑刺都必须在**独立上下文**里进行：任务只给改法稿、对象全文和获批清单，不给写改法时的推理过程。让作者带着完整上下文当自己的红队，考的是记忆不是方案。

1. **写改法（subagent 1）**：针对获批清单中的每条真问题与每项用户指定改动，逐条输出修改方案：
   - 对应哪条获批真问题，或哪项用户指定改动
   - 改动位置（精确到标题和原句）
   - 具体怎么改（给出可直接替换的文字，或唯一的语义修改说明）
   - 允许改动的边界
   - 预期结果：真问题写「改后哪项失败消失、为何对应完成条件会重新成立」；用户指定改动改写为**影响面清单**，逐一列出所有必须同步修改的位置（文件名与目录名、文件内的标识字段如 frontmatter 的 `name`、说明文档、安装或调用路径、其它文件里的交叉引用等）
   - 潜在风险
   - 故意不改什么
2. **挑刺（subagent 2）**：审查上述改法稿，专门挑出：与清单不符、破坏现有完成条件、遗漏获批条目、超出修改边界、以及用户指定改动的影响面清单是否有遗漏，作为「异议」。
3. **主 agent 裁决与定稿**：主 agent 逐条处理异议（采纳并调整改法，或依据原文驳回），整理出最终方案并写入笔记。

**完成标准**：挑刺在独立上下文中完成，未收到写改法时的推理过程；模型已按「评审阵容」分派，两者同模型时已在笔记标注；每条获批真问题、每项用户指定改动均有对应的具体改法；每项用户指定改动都带影响面清单；每条异议均有明确的采纳或驳回记录。

---

### 7. 闸门：最终方案

使用 `AskQuestion` 发起单选：

- 按这份方案改对象 (Recommended)
- 停

发送后立即停止，等待用户回复。

**完成标准**：用户确认按此方案修改。若方案的改法、边界、影响面清单或范围发生实质变化，必须回到第 6 步更新并重新过本闸门。

---

### 8. 改对象

1. **创建快照备份**：在编辑文件前，于系统临时目录创建唯一备份文件夹，无损备份每个修改对象的当前全文（包含未提交的工作区变更）。快照范围还须覆盖用户指定改动的影响面清单点到的全部文件——即使某个文件本身不属于适用对象三大类。
2. **原子执行**：严格仅修改最终方案点名的位置与内容，不得引入方案外的变更。改名一类波及多处的用户指定改动，必须在本步一次性改完影响面清单的每一项；不允许只改一半就进入验收。
3. **比对验收**：比对修改后文件与临时快照，核对 diff 是否与方案一致，确认真问题指出的可观察失败已消除、影响面清单逐项落地，且未破坏原有完成条件。
4. **清理备份**：步骤结束或终止时清理临时备份目录。

**完成标准**：修改内容严格与最终方案一致且无额外改动；所有真问题对应的失败均已消除；每项用户指定改动的影响面清单逐项已改，无遗留旧名或断链；对象原有的完成条件依然成立。

## 笔记规范

所有运行记录必须写入源码仓的 `docs/<父目录名>-<文件名>.md`。

**定位源码仓路径规则（按顺序取首个成立项）**：
1. 当前工作区根目录名为 `real-problems-skill` → 工作区根即为源码仓。
2. 本 skill 目录下存在 `source-root` 文件 → 读取第一行记录的绝对路径。
3. 均不成立 → 向用户询问源码仓绝对路径，获取后写入本 skill 目录下的 `source-root` 文件（该文件仅保存在本地，不提交进 git）。
