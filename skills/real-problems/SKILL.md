# real-problems

## 适用对象

仅处理已保存在本地磁盘上、且属于以下类别之一的文件：

1. **AI 提示词、技能与工作流**：
   - **Agent Skill**：技能定义文件（如 `SKILL.md`）
   - **系统提示词与角色规范**：System Prompt、Agent 指令约束、格式模板
   - **多 Agent 协作路由**：状态转移规则、任务交接契约、Eval 评测标准
2. **系统架构与工程规范**：
   - **Agent 指引与项目规则**：`AGENTS.md`、`.cursorrules`、系统规则配置
   - **架构决策与技术选型**：ADR（架构决策记录）
   - **工程标准与协作规范**：代码审查清单、分支管理规范、API 数据契约说明
3. **运维、安全与业务操作手册**：
   - **应急与运维预案**：故障止血 Runbook、数据库割接手册、灾备演练 SOP
   - **发布与环境规范**：金丝雀发布检查清单、环境搭建指南、权限审计 SOP
   - **产品与测试规范**：带有明确验收准则（AC / Given-When-Then）的需求规格与测试用例
4. **已有报告、稿件与专利草稿**（审查可定位问题）：
   - **报告**：各类已有报告 → 读 `references/reports.md`
   - **稿件**：技术、业务、研究、科普、新闻、演讲、宣传、文学与创意等已有稿件 → 读 `references/manuscripts.md`
   - **专利草稿**：已有技术交底书、申请文件或答复草稿 → 读 `references/patent-drafts.md`

路径相对本 `SKILL.md` 所在目录。只读命中的一份文类参考；检查项留在参考文件中，不复制到本文件。

### 特殊前置规则

- **修改对象、核对材料与其它指针**：
  - **修改对象**：原文明确要求修改、文件已存在且属于适用类别 → 并入修改对象并通读全文。
  - **核对材料**：模板、证据、图表、附图，或用户明确指定的核对件 → 必须通读并记路径；只传给相关评审者；默认不列入修改对象，第 8 步不动。
  - **其它指针**：按原文需要读取或引用，不列入修改对象，不默认传给所有评审者；记录排除理由。
- **前置阅读分流**：
  - 修改对象为 **Agent Skill**：主 agent 与所有 subagent 在提交草案或修改文件前，必须通读 `writing-for-agents` 的 `SKILL.md` 与同目录的 `SKILL-MECHANICS.md`，按当前宿主的 skill 清单和已知安装位置解析路径。确认不可读后，将依赖它的步骤标为 `blocked`，说明缺哪个和上游地址（https://github.com/mattpocock/skills 的 `skills/productivity/writing-for-agents`），并继续不依赖它的工作；`blocked` 的步骤不能报告为完成。
  - 修改对象属于第 4 类：主 agent 与第 3、6 步 subagent 必须通读命中的文类参考；同时读取与各自任务相关的核对材料。
  - 其它对象：跳过上述前置参考。
- **不适用场景（立即停止并指引正确途径，不自动调用）**：
  - 纯代码运行时报错排查 → 使用排查类 skill（如 `diagnosing-bugs`）
  - 业务需求与产品方案探讨 → 使用 `grilling`
  - 从零新建 Agent Skill → 使用 `create-skill`
  - 纯代码架构重构与拆模块 → 使用 `codebase-design`
  - 从零代写或无定位整篇重写报告、稿件、专利申请 → 不适用本流程
  - 文档无现成判据且无法提炼出任何可客观检验的完成条件 → 立即终止，说明无法按真问题流程继续

## 两类改动

本流程同时处理两类改动。两类改动的准入门槛不同，全程分开记录、分开列示，严禁混淆：

### 1. 用户指定改动
用户已经拍板、无需论证的诉求（如改名、改 `description`、换斜杠命令、统一术语）。
- **门槛**：不经过真问题的双重检验，用户提出即成立。
- **职责**：主 agent 原样登记诉求与目标，梳理受影响的全部位置（影响面清单），并在最后一步原子执行，不进行可行性论证。

### 2. 真问题
必须**同时满足以下两项硬性条件**的缺陷：
1. **能准确定位**：能指出原文中的具体位置、原句或可观察的行为。
2. **不改必定失败**：若不修改，对象无法达成已确立的完成条件，或与实际代码/环境脱节导致报错，或缺失关键异常/退出分支导致死锁卡死。

*注：对象的 id、斜杠命令和 `description` 仅能作为「用户指定改动」处理，不得记为真问题。*

## 执行步骤与闸门

### 闸门通则

只在缺少继续所需的事实、安全决定、范围决定或明确批准时提问。任务、仓库或本轮对话已经给出的答案和授权覆盖同一范围时，不重复询问。独立工作继续进行；只有依赖该答案的分支暂停。

1. 需要用户决定时，使用宿主提供的问答工具；没有该工具时用文字提出同等明确的问题。
2. 推荐项排第一并标 `(Recommended)`，但推荐项不是批准。
3. 明确批准仅对问题中列出的对象、范围和动作生效；范围或方案发生实质变化时重新取得批准。
4. 未回复不构成批准。需要批准的关口停在该关口并交付已完成的清单；不把沉默或超时记为批准。

### 1. 定对象

1. **锁定修改对象、核对材料与其它指针**：确认路径，按「特殊前置规则」逐一分类；修改对象与核对材料均读全文，其它指针记录处理方式与排除理由。
2. **判定文类**：对象属于第 4 类时，判定是报告、稿件还是专利草稿。专利草稿还须确认司法辖区、专利类型、申请阶段；缺一项不得默认套用中国或 PCT 规则。
3. **确定拟用规则**：列出对象原文、用户 brief、组织模板、平台规则或官方规范中拟作为判据的来源及版本。用户未指定、仅由调研发现的外部规则只能记为候选标准。
4. **通读全文与前置阅读**：通读修改对象、已标记的核对材料和命中的文类参考，严格执行前置阅读分流；未选规则只读不启用。
5. **登记用户指定改动**：原样记录用户提出的每一项改动诉求与目标，不评判、不论证、不改动文件。
6. **确定完成条件**：
   - 原文已写明判据：原样摘录作为基准。
   - 原文未显式写出，或用户指定了 brief、模板、平台规则、官方规范：提炼 2~4 条核心候选判据；这些判据在获批前只作为评审假设，不作为完成条件或修改依据。若不同判据会改变评审范围或修改权限，使用宿主问答工具提交确认；否则记录为本轮工作假设并继续，并在清单闸门列明任何依赖它的候选标准。
   - 第 4 类的每条候选判据必须列出本轮启用的文类参考项（标题与编号）；多个参考项可以归入同一条高阶判据。未被点名启用的参考项不是完成条件。
   - 无法提炼任何客观判据：立即终止流程并告知用户。
   - 缺文类准入信息与完成条件确认时，可合并为一次提问；本步补问不替代需要明确批准的修改关口。
7. **记录基准信息**：记录修改对象与核对材料的绝对路径、对象所在项目根目录（如有）、命中的文类参考、拟用规则及版本、获批完成条件与参考项映射、用户声明不动的部分，以及其它指针的处理方式。

**完成标准**：所有修改对象路径真实存在且属于适用类别；若标了核对材料，则均已读完并记路径；第 4 类已读命中的文类参考；专利草稿的司法辖区、类型、阶段已确认或已停止；用户指定改动逐项登记；完成条件全部源自原文或用户明确确认；第 4 类完成条件已点名启用的参考项；调研新发现且未获批的外部规则未被启用；所有指针均有唯一处理状态。

### 2. 闸门：调研、模式与模型分派

调研旨在**引入项目真实代码/环境事实或同类成熟规范，核实文档声称是否脱节并查漏补缺，防止闭门造车**。

调研范围、评审模式和模型分派是执行选项，不是修改批准。已有答案直接复用；没有用户偏好时采用推荐项并记录，不为这三项单独阻塞工作。只有「其它」缺少必要信息，或用户点名的模型无法解析时才提问：

**第一题 · 调研范围（多选）**：
- 调研项目代码与实际环境：对照核查文档声称的命令、脚本、路径、接口字段、环境变量与依赖在对象所在项目中是否真实存在且匹配 (Recommended)
- 对标同类规范与成熟实现：参考业界或同类项目的成熟流程，对照寻找对象中遗漏的关键异常处理、防御性校验或退出分支
- 其它（用户自行填写）
- 不调研

**第二题 · 评审模式（单选）**：
- **独立陪审团**：多名 subagent 独立完成同一轮完整评审（调研 + 读全文 + 报候选），彼此不通气。擅长发现未知问题，重复即强置信信号 (Recommended)
- **分区覆盖**：先集中调研只交事实，再按完成条件切成 2~4 个互不重叠的角度分头审查。节省上下文，易于证明无遗漏

**第三题 · 模型分派策略（单选）**：
- **分派不同模型**：同一轮的角色（陪审员之间、改法与挑刺之间）尽量分派两两不同的可派发模型，盲区不重叠，交叉重合即高置信信号 (Recommended)
- **使用相同模型**：所有 subagent 统一使用当前默认/继承模型，仅依靠独立上下文进行隔离
- **由我点名指定具体模型**：由用户按 Cursor 选择器显示名指定各角色模型（如 Gemini 3.8 Flash / Gemini Flash 3.8）；未提供时停下等待用户输入

#### 分支处理

- **调研分支**：
  - 勾选「不调研」：忽略其它调研选项，在笔记「调研」章节记录一行理由；评审模式与模型分派的选择依然生效。
  - 选「其它」：先检查核查目标是否明确、所需来源是否可访问、动作是否可执行；仅在缺少这些必要信息时请用户补充或改选。
  - 选「独立陪审团」：不在本步单独执行调研，调研并入第 3 步由每名陪审员各自独立完成；本步只整理调研范围说明，随任务下发。
  - 选「分区覆盖」：在本步执行集中调研。整理核查与对比清单，清单较长时按对象或对比维度分批并行派发 subagent（仅提供清单与对象所在项目根目录的绝对路径），subagent 逐项回报客观事实、一手证据及与原文出入，最后汇总为调研报告。
- **模型分派分支**：按第 3 步「评审阵容」执行。选「由我点名指定具体模型」且用户未给出名单时，先停下索取。

**调研硬边界**：调研只查证事实与提供对比证据，**严禁**把外部做法直接变成本地完成条件。调研认为应当补上的新判据必须记为**候选标准**单独编号列出，标明来源与理由，交由第 5 步闸门由人拍板。

**完成标准**：三项均已有选项（用户提供或采用推荐项）；选「不调研」已记录理由；选独立陪审团时调研范围说明已整理就绪待下发；选分区覆盖且有调研时已生成有据可查的汇总报告；新标准均记为候选标准，无直接越界使用者；模型分派策略已记录在案。需要用户提供的信息缺失时，只暂停依赖该信息的分支。

### 3. 独立评审

#### 评审阵容（模型分派规则）
适用于本步评审者与第 6 步改法/挑刺者。
- **核心底线**：**独立上下文**——每个 subagent 在自己的独立上下文里作业，互不通气，看不到同伴的结论。
- **可用 vs 可派发**：
  - **可用**：宿主实际提供且能运行 Agent 的模型。模型显示名或别名必须依据当前宿主的模型契约解析，不能凭名称猜测 ID。
  - **可派发**：当前父会话真正能把 subagent 跑起来的模型参数（含省略参数以继承父会话）。父会话工具说明里的 slug 举例名单不是可用全集，也不得拿来预检点名；点名后必须带解析所得 ID 去派发，以调用成败为准。
- **模型调度**：严格遵循用户在第 2 步拍板的策略。
  - 分派不同模型：在**可派发**集合里尽量两两不同；可派发数量不足时重复使用并在笔记标注。同模型重合结论在第 4 步不计入跨模型置信信号。可用但派发调用失败的模型，不得记成已经派出。
  - 使用相同模型：全部继承父会话模型，笔记标注单一模型。
  - 点名指定：按宿主解析出的 ID 写入该 subagent 的模型参数并派发。调用被拒绝时，报告点名原文、解析结果和拒绝信息并停止该评审分支；禁止静默改用继承或其它模型。其它不依赖该模型的工作继续。

#### 分支 A · 独立陪审团模式
1. 默认派出 3 名陪审员（产生 2/3、3/3 多数信号），用户可调整数量。按评审阵容分派模型。
2. 每名陪审员拿到**完全相同的完整输入**：修改对象全文及绝对路径、对象所在项目根目录、获批完成条件、用户声明不动的部分、第 2 步确定的调研范围；命中第 4 类时，再加对应文类参考及完成条件启用的参考项；只下发与本轮相关的核对材料。
3. 陪审员在**独立上下文**中各自独立完成整轮工作：先做调研，再通读上述输入，用获批完成条件、命中的参考项、核对材料和调研事实对照分析，彼此不串供。
4. 每份回报包含：本人调研拿到的事实与一手来源、候选清单、以及本人提议的候选标准（如有）。

#### 分支 B · 分区覆盖模式
1. 将第 1 步确定的完成条件与第 2 步的调研事实，划分为 2~4 个互不重叠的**角度**（如实际可行性对照、指令完整性、异常分支可判定性、术语一致性等）。
2. 并行派发 subagent 分头审查，每位 subagent 只拿单一角度的完成条件和对应事实；命中第 4 类时，再拿已启用参考项；只下发与该角度相关的核对材料。输出该角度下的候选清单与候选标准（如有）。

#### 候选通用格式
每条候选必须包含以下要素（无问题时明确标注「无候选」）：
- **位置及原文**
- **对应的完成条件（或项目实际脱节点、候选标准）**
- **文类参考项**（第 4 类必填）：写明已被完成条件启用的参考标题与编号
- **不改时能看见的失败（报错、死锁或无法达成目标）**

**完成标准**：
- 陪审团模式：陪审员数量合规，全员拿到完整输入并在独立上下文中产出，模型分派严格符合用户设定并在笔记中标注。
- 分区覆盖模式：划分为 2~4 个互不重叠角度，每条完成条件恰好归属一个角度，各角度输出回报。
- 共同标准：每条候选格式齐全，或注明无候选；第 4 类候选均能同时对应获批完成条件与已启用参考项。

### 4. 筛真问题

1. **编号与合并**：
   - 为所有候选赋予唯一编号。同因同果的候选予以合并，记录新编号及所有来源编号。
   - 陪审团模式下统计独立指出人数及**涉及的不同模型数**。清单先按不同模型数、再按指出人数降序排列（同模型多次指出仅按 1 个模型信号计）。
   - 分区覆盖模式下无重复则不合并。
   - 结论冲突时以原文和客观代码事实为准裁决。
2. **核验真问题**：依据真问题两项硬条件逐条审查候选，仅保留真问题。淘汰项逐一写明具体的丢弃原因；产品缺口（外部有但本对象未要求）一律淘汰，不得升级为真问题。第 4 类中未被获批完成条件点名启用的参考项，一律按产品缺口淘汰。
3. **处理候选标准**：统一编号并列明来源与理由。若某条真问题仅依赖某候选标准成立，标注「依据候选标准 Sn，待批」。
4. **关联调研事实**：为调研事实统一编号。能构成候选的保留转化映射，未构成候选的记入笔记「调研」章节（遇用户声明不动部分注明冲突内容）。
5. **分类成清单**：分两节独立列示——「用户指定改动」（照第 1 步登记原样列出不做筛选）与「真问题」（严格筛选结果），两节互不混淆。
6. **记录终点去向**：建立去向表，确保每个候选编号、调研事实编号和候选标准编号都有且仅有一个确定的最终归宿，绝不悬挂。
7. **记录笔记**：将两节清单、候选标准、丢弃原因及去向表写入运行笔记。

**完成标准**：所有编号均有唯一终点去向；真问题条目均符合定义，依赖候选标准已标注待批；用户指定改动与第 1 步登记一致无增减。

### 5. 闸门：清单

使用宿主提供的问答工具发起单选，问题中完整承载四部分：用户指定改动、真问题清单（含独立指出人数与不同模型数）、候选标准、丢弃原因。用户已明确批准同一清单时直接复用，不重复提问。

- 按这份清单继续 (Recommended)
- 保留清单并结束

只有明确选择「按这份清单继续」才进入后续改法；选择「保留清单并结束」则保留清单并结束。未回复不构成批准，交付清单后停在本闸门。

**完成标准**：用户明确选择继续，即视为同时批准三件事——真问题清单、清单所依赖的候选标准（升格为完成条件）及用户指定改动。后续仅处理获批内容；内容若有变动必须回到第 4 步重新过本闸门。用户选择「保留清单并结束」或未回复时，清单保留在笔记中，本轮不进入第 6～8 步。

---

### 6. 改法与异议

按顺序派发两个 subagent 进行方案设计与交叉审查（仅交稿，不直接改文件），模型分派遵照第 2 步确定策略。命中第 4 类时，写改法与挑刺均拿到修改对象全文、获批清单、对应文类参考、已启用参考项和相关核对材料。

第 4 类只设计有界修改：每处改动须点名原句、段落或栏目，并对应获批条目；禁止没有逐项映射的整篇重写。专利草稿只有在已确认申请阶段和拟用规则明确允许修改范围时才设计替换，否则只保留问题清单。

**挑刺必须在独立上下文里进行**：任务仅提供改法稿、修改对象全文、获批清单，以及第 4 类命中的参考项和相关核对材料，**严禁提供写方案时的推理过程**，避免作者自带完整上下文当自己的红队。

1. **写改法（subagent 1）**：针对获批的每条真问题与每项用户指定改动逐条给出方案：
   - 对应的获批真问题或用户指定改动编号
   - 精确修改位置（标题与原句）
   - 具体改法（可直接替换的文字，或唯一的语义修改说明）
   - 允许改动的边界与故意不改项
   - 预期结果：真问题写明消除何种失败、为何完成条件重新成立；用户指定改动改写为**影响面清单**（逐一列出文件名、目录名、frontmatter 字段、说明文档、安装/调用路径及外部引用等所有必改点）
   - 潜在风险
2. **挑刺（subagent 2）**：在独立上下文中审查改法稿，专门挑出：与清单不符、破坏现有完成条件、遗漏获批条目、超出修改边界、影响面清单遗漏等问题，作为「异议」。
3. **主 agent 裁决与定稿**：主 agent 逐条处理异议（采纳调整或据理驳回），整理出最终方案并记入笔记。

**完成标准**：挑刺在独立上下文完成且无推理过程输入；模型分派符合规定并在笔记标注；获批条目均有改法；用户指定改动均带影响面清单；异议均有明确采纳或驳回记录。第 4 类改法均已点名修改边界，无整篇重写；专利草稿的替换范围有已确认规则依据，否则未进入改对象。

---

### 7. 闸门：最终方案

使用宿主提供的问答工具发起单选；用户已明确批准同一方案时直接复用：

- 按这份方案改对象 (Recommended)
- 停

只有明确选择「按这份方案改对象」才开始修改；选择「停」或未回复时停在修改前。

**完成标准**：用户明确确认按此方案修改，或当前对话已有覆盖同一方案、边界和范围的明确授权。方案改法、边界、影响面清单或范围若发生实质变化，必须回到第 6 步更新后重新过本闸门。

---

### 8. 改对象

1. **创建快照备份**：编辑前在系统临时目录创建唯一备份文件夹，无损备份每个修改对象（含未提交变更）及影响面清单点到的全部文件。
2. **原子执行**：严格仅修改最终方案点名的位置与内容，绝不夹带方案外改动。改名等波及多处的用户指定改动，必须一次性改完影响面清单中的每一项，严禁留半截。第 4 类只执行最终方案逐项点名的原句、段落或栏目改动，禁止无映射的整篇重写。核对材料默认不改；专利草稿不得超出已确认规则允许的修改范围。
3. **比对验收**：比对修改后文件与临时快照的 diff，核对方案精确落实、真问题指出的可观察失败已消除、影响面清单逐项落地、原有完成条件未被破坏。方案未点名的核对材料不得出现在 diff 中。
4. **清理备份**：验收通过后清理临时备份目录；失败或中断时保留恢复所需备份并报告位置，确认恢复或不再需要后再清理。

**完成标准**：修改严格吻合最终方案且无额外变动；所有真问题对应的失败已消除；影响面清单项全部落实无残留；原有完成条件依然成立。

## 笔记规范

所有运行记录默认写入当前任务源码仓的 `docs/<父目录名>-<文件名>.md`。当前任务已有的工作区、对象所在的 Git 根目录或用户明确给出的源码仓优先；不要为了定位安装该 skill 的作者仓库而提问。

**源码仓路径定位规则**：
1. 用户明确给出的源码仓或修改对象所在的 Git 根目录。
2. 当前工作区根目录；若它就是 `real-problems-skill`，直接使用该目录。
3. 仅当用户明确要求把笔记写回 skill 源码仓，且前两项都不适用时，才询问该仓库路径；不要在安装目录写入 `source-root`。
